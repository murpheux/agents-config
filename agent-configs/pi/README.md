# Pi — Murpheux's Global Configuration

Global configuration for [Pi](https://pi.dev) (`@mariozechner/pi-coding-agent`, github.com/earendil-works/pi), ported from the [OpenCode](../opencode) baseline that is the source of truth for this repo. Pi is architecturally different from OpenCode: **one model, one session, no subagents, no permission-rule or hook file** — tool calls run with the OS permissions of the account that started Pi. Everything here is built to Pi's own documented mechanisms, not a re-skin of OpenCode's policy engine.

> This folder is hand-maintained, like `../opencode`. It is **not** wired into `_shared/build.py` — Pi isn't part of the generated-tool pipeline (`claude-code/`, `vscode/`, `cline/`, `codex/`, `github-copilot-cli/`, `aider/`), so changes here never touch, and are never overwritten by, anything under `_shared/`.

## Layout

```text
~/.pi/agent/                  # Pi's agent directory (override with $PI_CODING_AGENT_DIR)
├── AGENTS.md                 # global instructions + security guardrails — Pi loads this natively
├── settings.json             # default model/thinking level, default tools, project-trust policy
├── mcp.json                  # MCP servers (GitHub, Context7, MS Learn, AWS docs, Terraform registry)
├── models.json                # agentgateway + openrouter provider/model definitions
├── extensions/
│   └── guardrails.ts         # tool_call hook: the hard-deny / protected-path rules (Pi has no
│                              # declarative permissions file, so this is Pi's enforcement layer)
├── skills/                   # on-demand instructions, routed by description or /skill:<name>
│   ├── role-{developer,sre,architect,reviewer,security,planner}/   # ported from _shared/agents/*.md
│   └── {adr,ansible,architecture-diagrams,aws,azure,bash,docker-swarm,dotnet,drawio-diagrams,
│        github-actions,golang,homelab,image-generation,incident-response,kubernetes,nodejs,
│        powershell,python,terraform,threat-modeling}/                # ported from opencode/skills
└── prompts/                  # slash commands: /review /commit /plan /test /explain /summarize /pr
                               # /scaffold /security-scan /iac-review /threat-model /adr /incident
                               # /cost-review /diagram /image
```

## Why there are no `agents/` or `permissions.json` files

Pi has no concept of subagents, and no hooks/permission-rule config file — confirmed against `pi.dev/docs/latest/{configuration,extensions,security,cli}`:

- **No subagents.** The SDK exposes one `AgentSession` per conversation; there is no API for spawning named child agents with their own model/tool set the way OpenCode's `agents/*.md` or Claude Code's subagents do. The 7 OpenCode personas (`router`, `explorer`, `developer`, `sre`, `planner`, `architect`, `reviewer`, `security`) are *not* rendered as separate agent files here.
  - `router` and `explorer` have no Pi equivalent worth packaging: in a single-session tool, **you are the router** (deciding what to invoke and when), and "explorer" is just the always-available `read`/`grep`/`find`/`ls` built-ins used directly.
  - `developer`, `sre`, `architect`, `reviewer`, `security`, `planner` *are* packaged — as **Skills** (`skills/role-*/SKILL.md`), ported verbatim from the same tool-neutral `_shared/agents/*.md` bodies the other 6 tools in this repo use for their subagents. Pi routes them automatically from their `description`, or you force one with `/skill:role-developer` etc. They change *behaviour and process*, not the underlying model — switch model yourself (`/model …` or `--model`) alongside them if a role calls for a different tier.
- **No permissions/hooks file.** Pi's own docs are explicit: "Pi can read, change, and execute files with the permissions of the account that started it, and it does not ask for approval before every tool call." The only declarative gate is **project trust** (`defaultProjectTrust` in `settings.json`), which governs whether Pi loads a project's own `.pi/` config at all — not per-tool-call approval. The documented way to gate individual tool calls is a `tool_call` **extension** handler, so that's what `extensions/guardrails.ts` is: a hand-port of this repo's shared `_shared/guardrails/guardrails.json` rule set (33 command rules, protected paths) into Pi's own extension API, modelled directly on Pi's own `examples/extensions/protected-paths.ts`. It is **not** generated by `_shared/build.py` and must be kept in sync by hand if `guardrails.json` changes.

## MCP servers (`mcp.json`)

| Server | Transport | Needs |
|---|---|---|
| `github` | remote (`api.githubcopilot.com/mcp/`) | `GITHUB_PAT` env var; read-only toolset |
| `context7` | remote | `CONTEXT7_API_KEY` env var |
| `mslearn` | remote | none (official, free) |
| `awsdocs` | local (`uvx awslabs.aws-documentation-mcp-server@latest`) | `uv` on PATH |
| `terraform` | local (`docker run hashicorp/terraform-mcp-server`) | Docker |

Deliberately **not** configured, matching the OpenCode baseline's own reasoning: a 1Password-reading MCP server (an LLM with vault access is a prompt-injection exfiltration path — use `op plugin run -- <cmd>` instead, which never puts secrets in model context) and the Agentgateway MCP endpoint (its path was never confirmed working in the OpenCode config either). Add either only after reviewing the trade-off yourself.

## Models (`models.json` + `settings.json`)

Pi has no per-skill or per-agent model binding (that's an OpenCode-specific feature of `opencode.jsonc`'s `agents.<id>.model`), so the OpenCode cost-tier map is carried over as **manual switches** instead:

| Tier | Model | Switch with |
|---|---|---|
| cheap | `agentgateway/deepseek-flash` | `/model agentgateway/deepseek-flash` |
| workhorse (default) | `agentgateway/claude-sonnet-5-5` | default; `modelThinkingLevels` pins it to `medium` |
| reasoning | `agentgateway/gpt-6.1-sol` or `openrouter/openai/gpt-6-sol` | `/model … --thinking high` |
| premium | `agentgateway/claude-opus-5-5` or `openrouter/anthropic/claude-opus-5.5` | `/model … --thinking high` — HIGH_RISK/security only |

`agentgateway` is a custom provider for the same gateway OpenCode uses, with two wire formats, mirroring `opencode.jsonc`:

- `deepseek-flash`, `gpt-6.1-sol` → `openai-completions` at `https://scarlet:9443/v1`.
- `claude-sonnet-5-5`, `claude-opus-5-5` → per-model `api: "anthropic-messages"` at `https://scarlet:9443` (the Anthropic SDK appends `/v1/messages`). Claude 5.5 rejects the `thinking.type=enabled` that a chat→Anthropic translation sends, so these speak the Messages API directly with `compat.forceAdaptiveThinking` and `supportsTemperature: false`. Context/output/thinking metadata is copied from Pi's built-in `anthropic` catalog entries. An `Authorization: Bearer` header is sent alongside `x-api-key`, as OpenCode does.

`openrouter` is **not** in `models.json`: it is a built-in Pi provider (own catalog and API adapter), enabled automatically by `OPENROUTER_API_KEY` or `/login openrouter`. Redefining it would replace that catalog with bare entries. The `openrouter/…` IDs in `settings.json` all exist in the built-in catalog.

`modelThinkingLevels` in `settings.json` is the equivalent of OpenCode's explicit `#medium`/`#high` reasoning-effort variants.

If you also run a local Ollama (as the OpenCode config does, pointed at `medusa:11434`), add it yourself with the exact model id(s) you've pulled (`ollama list`) — this repo doesn't guess at what's installed on your machine:

```json
"ollama": { "baseUrl": "http://medusa:11434/v1", "api": "openai-completions", "apiKey": "ollama", "models": [{ "id": "<your-pulled-model>" }] }
```

## Setup checklist

```bash
# 0. Install (backs up what it replaces to ~/.agent-config-backups/pi-<timestamp>/):
cd ~/AI_Workspace/Projects/agents-config/agent-configs/pi && DRY_RUN=1 ./install.sh && ./install.sh
```

```bash
# 1. Environment (via 1Password / shell profile — never in this repo)
export AGENTGATEWAY_API_KEY=...   OPENROUTER_API_KEY=...   GITHUB_PAT=...   CONTEXT7_API_KEY=...

# 2. Trust the gateway's private TLS cert. Pi runs on Node, which ignores the macOS keychain,
#    so without this every agentgateway request fails with "Connection error."
#    Never disable verification (NODE_TLS_REJECT_UNAUTHORIZED=0) instead.
export NODE_EXTRA_CA_CERTS=/Users/Shared/nfs_share/docker_volumes/agentgw/tls/cert.pem

# 3. Verify
pi --list-models
pi mcp list
```

`NODE_EXTRA_CA_CERTS` must name the **CA** that signed the gateway cert (a self-signed leaf also works), the cert's SAN must include `scarlet`, and the file must be readable when Pi starts. It lives on the NFS share, so Node silently skips it if the share isn't mounted.

Requirements for optional MCP servers: `uv` (awsdocs), Docker (terraform). Remove either server from `mcp.json` if unused.

## Troubleshooting

| Symptom | Check |
|---|---|
| Skill not routing | frontmatter `name` is lowercase-hyphenated and matches the directory; `description` is set; `/reload` after editing |
| `/skill:role-developer` not found | run `pi mcp list`/`--list-models` style sanity check is unrelated — check `enableSkillCommands: true` in `settings.json` and that the skill directory contains `SKILL.md` |
| `Connection error.` on agentgateway | TLS/DNS/TCP, not auth (a missing key gives "Failed to resolve…"). Show the real cause with the Node one-liner below |
| Model unavailable | the model `id` exists under the right `providers.<name>.models` entry in `models.json`; `pi --list-models` |
| A blocked command was legitimate | `extensions/guardrails.ts` is intentionally strict — adjust the rule there (keep it in sync with `_shared/guardrails/guardrails.json` by hand) rather than routing around it |
| MCP server won't start | `~/.pi/agent/mcp.log` (rotates to `mcp.log.1` at 5 MB); `pi mcp list --json` |
| Project config not loading | Pi gates `.pi/settings.json`, `.pi/mcp.json`, `.pi/extensions`, `.pi/skills`, `.pi/prompts` behind project trust — `defaultProjectTrust` is `ask` here, so the first run in a new project prompts for it |

Pi's "Connection error." hides the underlying cause. This uses the same Node binary as Pi and prints it:

```zsh
/opt/homebrew/opt/node/bin/node -e 'fetch("https://scarlet:9443/v1/models").then(r=>console.log("HTTP",r.status)).catch(e=>console.log(e.cause?.code,"-",e.cause?.message))'
```

| Output | Meaning |
|---|---|
| `HTTP 200`/`401` | Transport works; Pi should connect |
| `UNABLE_TO_VERIFY_LEAF_SIGNATURE` / `SELF_SIGNED_CERT_IN_CHAIN` / `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` | `NODE_EXTRA_CA_CERTS` unset, unreadable, or not the signing CA |
| `ERR_TLS_CERT_ALTNAME_INVALID` | Gateway cert has no `scarlet` SAN |
| `ECONNREFUSED` / `ENOTFOUND` | Wrong port / name doesn't resolve |

For untrusted or fully autonomous work, run Pi inside a container or VM — see `security.md#containerization` in the Pi docs; there is no in-app sandbox to fall back on.
