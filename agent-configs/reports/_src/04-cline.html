Folder: ~/agent-configs/cline/ → Documents/Cline/ (both builds) and ~/.cline/ (next + CLI)

1. Summary

Since 4.1.0 one extension package ships two builds with different config homes: legacy and SDK-based next, which shares everything with the CLI. The configuration targets both:

  • Both builds: rules, workflows and hooks, in Documents/Cline, which both builds read.
  • next + CLI: skills, defined subagents, the guard and MCP, in ~/.cline.

Routing uses Plan mode (strong model) and Act mode (workhorse), plus defined subagents. Cline subagents don't inherit approval settings, so every one is read-only by design; all mutations happen in the Act session, where approvals and the hook apply.

5. Guardrails

  1. Guard hook on both builds cancels destructive, secret-reading, force-push and interactive commands, and secret-file access through read_files, editor and apply_patch. It was tested with both payload shapes and with Windows PowerShell.
  2. Read-only subagents, because they bypass approvals.
  3. Approvals: Edit and Execute set to require approval. next defaults to auto-approving edits and MCP, so this has to be changed in the UI.
  4. Legacy extras: the CLINE_COMMAND_PERMISSIONS deny list (deny wins, with no allow list so everything else still prompts) and .clineignore, which is not a security boundary.
  5. Credentials: MCP servers are launched through op run; providers read env keys, so nothing secret is stored.

6. awesome-clinerules assessment

The list is a copy of awesome-cursorrules: 131 .cursorrules folders, last updated January 2025, and many files are squashed onto a single line. It has nothing for .NET, PowerShell, bash, Terraform/Ansible, cloud, security or diagrams, and its globs: frontmatter is ignored by Cline (which uses paths:).

Ideas adopted into the global rule and the skills:

  • verify before assuming, and make the minimal change;
  • answer-length control (fewer output tokens);
  • respect the existing architecture;
  • stdlib-first Go;
  • uv, ruff and pytest for Python;
  • strict TypeScript;
  • the project-notes / memory-bank pattern.

The gaps were filled from cline/prompts (security audit, Mermaid plans, memory bank) and the shared skills.

7. Gotchas handled

  • Two builds, two config worlds: files are placed where both builds read them, and pinning next is recommended.
  • Linux Documents directory: it is resolved via xdg-user-dir. On Windows install.ps1 uses the real MyDocuments folder, which handles OneDrive redirection.
  • Windows hooks: only PreToolUse.ps1 runs, and the Windows installer removes the POSIX launcher. Unsigned scripts on UNC paths are blocked, so the installer is run from a local copy.
  • Defaults to watch: the CLI defaults to --auto-approve true, and the next build dropped the per-tool MCP autoApprove list.

8. Validation

All frontmatter and JSON parse; the 4 subagent definitions have the required keys. The installer smoke test showed the hook cancelling a force-push (next payload) and allowing go test (legacy payload), with MCP paths rendered. On Windows, the real PreToolUse.ps1 blocked Remove-Item -Recurse -Force C:\ and allowed dotnet test.
