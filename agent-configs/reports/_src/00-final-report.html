1. Executive summary

The cost-aware multi-agent configuration built for OpenCode was re-implemented natively for Claude Code, GitHub Copilot CLI, VS Code (Copilot Chat), Cline, OpenAI Codex CLI and Aider. Each tool has its own folder that mirrors its real home-directory layout, with an installer that backs up anything it replaces. Nothing was installed into live locations.

All seven configurations are generated from one source of truth:

  • the OpenCode AGENTS.md (every fact preserved; 277 items checked in each of the six new instruction files);
  • eight tool-neutral agent prompts;
  • 16 shared workflows;
  • 20 portable skills (Agent Skills spec);
  • one guardrail rule set with a single guard hook that speaks five hook contracts.

Current config formats were confirmed for each tool (September 2026 versions), and ideas from each awesome list were adopted where they fit. Everything was validated offline:

  • parsers for every config format;
  • Starlark rules executed with their examples;
  • 70 guard self-tests;
  • 34 installer smoke checks in throwaway homes;
  • the Windows PowerShell hook run for real.

2. Approach

  1. Research: six parallel research agents read each tool's official sources on GitHub, because the corporate proxy blocks many AI vendor sites. Each also read its awesome list:
    • awesome-claude-code → Claude Code;
    • awesome-copilot and awesome-copilot.github.com → Copilot CLI and VS Code;
    • awesome-clinerules → Cline;
    • awesome-codex-cli → Codex;
    • Aider community resources (no list was provided).
    The Copilot CLI agent stalled. It was replaced by the installed CLI's own help (v1.0.61) and the github/docs references.
  2. Shared layer: _shared/build.py turns the OpenCode baseline into a placeholder template, portable skills, agent bodies and commands. It renders each tool from a small YAML spec and normalises line endings.
  3. Tool layer: settings, providers, MCP, hooks and permissions were written per tool, using only keys confirmed for the current version.
  4. Verification: validate.py and install_smoke.sh, a content-preservation check, and Windows tests.

7. Coexistence on one machine

  • ~/.copilot is shared by the Copilot CLI and VS Code's Copilot harness. Both folders install identical instructions, skills and hooks; agents are target-scoped (github-copilot vs vscode).
  • ~/.agents/skills (Codex) is also read by the Copilot CLI and Cline next. The Copilot and VS Code installers skip identical copies; Codex workflow skills live in Codex-only ~/.codex/skills.
  • VS Code's Copilot harness also reads ~/.claude/agents and ~/.claude/skills. chat.useClaudeMdFile is off so CLAUDE.md isn't loaded twice, but Claude agents will show in VS Code's picker if both are installed.
  • Windows + WSL: each harness reads the host it runs on. Run the Windows install.ps1 (from a local copy, because UNC scripts are blocked by RemoteSigned) and the WSL install.sh.

10. Limitations & assumptions

  • Model ids follow each tool's catalog at verification time. Confirm them once in each picker; VS Code agents fall back to Auto.
  • Gateway and OpenRouter compatibility: LiteLLM /v1/responses for Codex, Anthropic pass-through for Claude, and reasoning_effort passthrough are assumed. They are optional overlays where uncertain.
  • Cline: provider, Plan/Act model and auto-approve choices live in extension state, so they are documented, not written.
  • Aider prices in model.metadata.json are placeholders.
  • The guard is a strong guardrail, not a sandbox. The OS sandboxes (Claude, Copilot, VS Code, Codex) and least-privilege credentials remain the real boundary.
